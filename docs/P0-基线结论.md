# P0 基线结论（第一轮）

日期：2026-10-17 ｜ 样本：Retera 自带 10 个粒子模型（1111–1906 B）｜ 工具：`mdx-toolkit/`

---

## 一、三条结论

| # | 结论 | 影响 |
|---|---|---|
| 1 | **现引擎不是字节级无损**：10/10 样本往返后都有差异 | 证实「不能用重序列化」——必须走 delta 透传 |
| 2 | 差异分两类：**良性规范化**（10/10，3 字节）与**结构性改写**（1/10，57 字节） | 后者才是真正会伤模型的那类 |
| 3 | **容器层本身是 100% 无损的**：解析→重建 26 项断言全过 | 透传方案技术上成立，可以往下走 |

---

## 二、先修正上一轮的一个误判（已再修正一次）

最初我说差异是"未知 chunk 的 tag 被清零"——**错了**。
后来我说是 `animFileName` 字段残留——**也错了**（当时靠猜布局）。

查 Retera 源码 `ModelChunk.java` 后确认，`MODL` 的真实布局是：

```
name[336] + unknownNull(u32) + boundsRadius(f32)
          + minExtent(3×f32) + maxExtent(3×f32) + blendTime(u32)   = 372 字节
```

差异位置 offset 356–358 落在 **`name[336]` 字段的尾部（+332）**，原始值是 `PDR` 三个字节，往返后被清零。
也就是：**模型名字段尾部有历史残留字节，Retera 保存时清干净了**。语义无害。

> 教训：格式布局不能靠猜。`TEXS` 同样被我猜错过——它**没有计数字段**，
> 每条固定 268 字节（`replaceableId + path[256] + unknownNull + flags`），读到块尾为止。
> 这正是"移植而非创作"这条技术路线的价值所在。

---

## 三、第一类差异：良性规范化（10/10）

| 项 | 值 |
|---|---|
| 出现率 | 10 / 10 |
| 差异字节 | 3（固定） |
| 位置 | `MODL.animFileName[+252]` |
| 原始 → 往返 | `50 44 52`（"PDR"）→ `00 00 00` |
| 性质 | 清理字符串字段的残留尾巴，语义无害 |

---

## 四、第二类差异：结构性改写（1/10，仅 WeaponMagicFlatEmitter.mdx）

`PRE2`（ParticleEmitter2）块 **922 字节，大小完全不变**，但内部子记录顺序变了：

| 文件 | `KP2*` 子记录出现位置 | 顺序 |
|---|---|---|
| 原始 | 271 / **738** / **794** / 842 | KP2V → **KP2E** → **KP2V** → KP2N |
| 往返后 | 271 / **738** / **786** / 842 | KP2V → **KP2V** → **KP2E** → KP2N |

**Retera 把第 2、3 个子记录（KP2E 与 KP2V）交换了位置。**

这类问题比第一类严重得多：大小不变、肉眼看不出来、用 Retera 自己重新打开可能还是对的，但**别的工具、或者进游戏后，粒子的可见性/发射行为可能就不对了**。

> 这正是需要差分台的理由——这种 bug 靠人眼永远发现不了。

---

## 五、为什么这一轮数据值得重视

如果我们采用"读进来 → 全量重新序列化 → 写出去"的做法：

- 用户只改了一个贴图路径
- `PRE2` 也会被重排
- 粒子表现可能变化，而用户永远不会知道是自己改贴图导致的

而按 delta 透传设计：**只重写 TEXS，PRE2 一个字节都不碰**，这个问题从架构上消失。这不是洁癖，是唯一正确的做法。

## 六、容器层已完成（P1 的前提）

`tools/selftest.py`，26 项断言全过：

| 测试组 | 内容 | 结果 |
|---|---|---|
| 1 | 解析 → 重建 == 原始（10 个样本） | ✅ 全部逐字节相同 |

## 七、这轮样本的局限（必须说清）

10 个样本都是 **1–2 KB 的纯粒子特效**，只有 `VERS / MODL / SEQS / TEXS / PIVT / PRE2` 六个块的类型组合。

**它没有覆盖真实单位模型的核心结构**：`GEOS`（几何）、`BONE`、`MTLS`（材质）、`GEOA`（几何动画）、`HELP`、`ATCH`、`RIBB`、`EVTS`、`CLID`、`BPOS`、`FAFX`。

所以这轮的价值是"证明工具链可用 + 证明 delta 必要"，**还不能给出真实资产的保真度数字**。下一步必须用真实模型跑。

# 第二轮：真实 Reforged 资产（11 个，2.5 KB – 4.3 MB）

`GEOS GEOA BONE MTLS TEXS ATCH LITE PRE2 CORN RIBB EVTS CAMS CLID FAFX BPOS GLBS`。

## 结果

| 文件 | 大小变化 | 差异字节 | 落点 |
|---|---:|---:|---|
| alchemy_rack | 不变 | 104 | BONE |
| Arcane Arrow | 不变 | **0** | — |
| **BigBookshelfClean** | **61262 → 60320（−942）** | 16068 | **GEOS** |
| BotanistGarden | 不变 | 395 | BONE |
| kultiranbarracks | 不变 | 304 | BONE |
| kultiranbarracks_portrait | 不变 | 304 | BONE |
| **kultiranbarracksdeath** | **2846255 → 2809936（−36319）** | 70334 | **GEOS** |
| David | 不变 | **0** | — |
| David_Portrait | 不变 | **0** | — |
| Lvbu | 不变 | 592 | BONE |
| Lvbu_Portrait | 不变 | 296 | BONE |

**3/11 逐字节相同，8/11 有差异，0 个转换失败。而且只动了两种 chunk：BONE 和 GEOS。**

## 类型 A：BONE 索引重编号（6 个文件，104 – 592 B）

每条骨骼记录里有 **2 个原本为 `0xFFFFFFFF`（-1）的 4 字节字段**，往返后变成递增序号：

```
原始     ffffffff ffffffff
往返后   00000000 00000000   ← 第 1 条骨骼
         01000000 01000000   ← 第 2 条
         02000000 02000000   ← 第 3 条
```

每个骨骼 8 字节，`alchemy_rack` 13 条骨骼 = 104 字节，与实测完全吻合。

**性质待定**：WC3 里节点的 objectId / 父级引用常被写成 -1（表示不使用），Retera 保存时按顺序重新编号。如果所有引用被一致重编号，语义等价；**如果有别的地方仍按旧编号引用，就会错位**。这一条必须用游戏内验证来判定。

## 类型 B：GEOS 结构性重写（2 个文件，文件变小）

这两个是**唯一真正的数据丢失**：

- `BigBookshelfClean`：−942 字节
- `kultiranbarracksdeath`：−36319 字节（-1.3%）

差异特征：原始文件里有一段 `0xFF…` 填充区（`BigBookshelfClean` 处为 948 字节），
Retera 用 `MTGC` 子块（Reforged 的矩阵组扩展）替换了它，并重排了 `MATS` / `TANG` 子块，
导致后续所有字节整体移位。

**这是"打开再保存就掉数据"级别的行为**，而且大小变化是唯一的外部线索——如果大小刚好不变，肉眼和工具都发现不了。

## 结论

| # | 结论 |
|---|---|
| 1 | 用「读入 → 全量重序列化 → 写出」改造这个引擎，**在 HD 模型上会丢数据**，不可接受 |
| 2 | 只改一个贴图路径，也会连带重写 GEOS —— 用户永远查不出是自己改坏的 |
| 3 | **delta 透传从"最佳实践"升级为"唯一可行路径"**：只改 TEXS，BONE 和 GEOS 一个字节都不碰 |
| 4 | 3/11 能做到 100%，说明格式本身没有根本障碍，问题全在"重写策略"而不是"能不能解析" |

## 待验证

BONE 的重编号到底是"修复"还是"破坏"，只有一条路能判定：**把往返后的模型放进 WC3 里看是否正常**。
这是人工步骤，需要你来跑。

# 第三轮：根因定位（GEOS 顶点组）

## 已确认良性：BONE 索引重编号

`alchemy_rack`、`kultiranbarracks` 往返后在**编辑器和游戏内测试均正常显示**。
结论：-1 → 递增序号 的重编号是**等价改写**，不影响运行。BONE 从风险清单移除。

## 已定位根因：GEOS 的 GNDX 被清零

Reforged 的 `GEOS` 块内部是标签化的子块序列：

```
VRTX → NRMS → PTYP → PCNT → PVTX → GNDX → MTGC → MATS → TANG → SKIN → UVAS → UVBS
```

Retera 保存时把 **GNDX（顶点组）的计数写成 0**，整段数据消失，其余子块字节数完全不变、只是整体前移。

| 模型 | geoset | 原始 count | 保存后 | 丢失字节 |
|---|---|---:|---:|---:|
| BigBookshelfClean | #0 | 942 | 0 | 942 |
| kultiranbarracksdeath | #0 | 23269 | 0 | 23269 |
| kultiranbarracksdeath | #1 | 144 | 0 | 144 |
| kultiranbarracksdeath | #2 | 5574 | 0 | 5574 |
| kultiranbarracksdeath | #3 | 1608 | 0 | 1608 |
| kultiranbarracksdeath | #4 | 5724 | 0 | 5724 |

丢失总量 36319 字节 = 文件缩小量 36319 字节，**逐字节对上**，排除任何其他解释。

## 影响判断（待游戏验证）

运行时渲染依赖 `MTGC/MATS`（矩阵组/矩阵索引）与 `SKIN`（蒙皮），
`GNDX` 主要用于**编辑期的顶点分组**，因此**很可能视觉完全正常**，属于"编辑元数据损失"。

但无论验证结果如何，**新内核必须正确实现 GNDX，不能继承这个 bug**。

## 对比测试包

# 第四轮：风险全部闭环（用户实测）

用户把两对 GEOS 模型（BigBookshelfClean、kultiranbarracksdeath 的 A/B 版本）
放进编辑器和游戏对比，**结论：没有任何区别**。

## 风险登记表（封板）

| 差异类型 | 出现率 | 实测结果 | 结论 |
|---|---|---|---|
| MODL `name` 字段残尾清理 | 10/10（小样本） | 不影响 | 良性规范化 |
| BONE 索引重编号（-1 → 序号） | 6/11 | 编辑器 + 游戏均正常 | 良性 |
| GEOS `GNDX`（顶点组）清零 | 2/11 | 编辑器 + 游戏均正常 | **视觉无害，但属于数据丢失** |

## 这组实测真正证明了什么

1. **Retera 的写盘路径不可信**：它会在用户不知情的情况下丢掉顶点组数据，而视觉上完全正常——
   这意味着**使用者永远发现不了**，直到某天需要按顶点组编辑时才发现元数据没了。
2. **"游戏里看着没问题"不能作为正确性标准**。保真度必须靠字节级断言，不能靠肉眼。
3. 因此新内核的处理原则定死：**顶点组必须原样保留**，不是因为它影响渲染，
   而是因为它是用户资产的一部分——"看不见"不等于"可以丢"。
